    Azure Kubernetes Service (AKS)

    Compatible with the azure-mgmt-containerservice SDK, the az aks CLI, Terraform's azurerm_kubernetes_cluster, and any ARM-speaking client.

    Requires Docker (in real mode): each AKS cluster is a k3s server container playing the managed control plane, plus one k3s agent container per agent pool node, on a Docker network of its own. Set FLOCI_AZ_SERVICES_AKS_MOCKED=true for a lightweight mock that skips Docker entirely.

    Every AKS name, label, default and error code below was checked against Microsoft's documentation, the AKS REST specification or the Azure clients' source; the Sources section lists them. Where a behavior could not be verified, the page says so.

    Features

    • Clusters: CreateOrUpdate, Get, Delete, List (by subscription and by resource group), UpdateTags, start, stop
    • Long-running operations: PUT answers 201/200 with Azure-AsyncOperation; DELETE, start and stop answer 202. The operation reports InProgress until the containers reach what was asked, then Succeeded, or Failed with the cause
    • Kubernetes versions: kubernetesVersion picks a pinned k3s image per minor version; kubernetesVersions, upgradeProfiles/default, availableAgentPoolVersions and the agent pool upgrade profile list what the emulator runs; upgrades recreate the server on the new image with the same data
    • Agent pools are nodes: each node is a k3s agent registered under its AKS name, with AKS labels, taints, zones, VMSS provider ID, and CPU and memory limits from its VM size; count changes add or remove nodes
    • GPU sizes: NC, ND and NV nodes carry kubernetes.azure.com/accelerator=nvidia and advertise nvidia.com/gpu
    • Storage classes as AKS creates them, with claims that bind
    • Networking: networkProfile pod and service ranges and DNS address applied to k3s, with AKS's defaults
    • Credentials: listClusterUserCredential (clusterUser) and listClusterAdminCredential (clusterAdmin) kubeconfigs laid out as AKS writes them; disableLocalAccounts refuses the static ones
    • Microsoft Entra ID: aadProfile, the kubelogin user kubeconfig, Entra tokens authenticated by a token webhook, admin groups bound to cluster-admin
    • Azure RBAC: enableAzureRBAC authorizes requests against role assignments through an authorization webhook, with AKS's data actions and Forbidden message
    • Workload Identity: the OIDC issuer (on by default), service account tokens under its AKS-format URL, the upstream mutating webhook add-on, and the token exchange at floci-az's Entra from pods (floci-az TLS required)
    • LoadBalancer Services: an Azure-shaped address in status.loadBalancer, public from 198.51.100.0/24 or internal on the cluster network, held by an appliance container that forwards to the nodes
    • Restore: in a persistent storage mode, clusters come back at startup on their surviving containers or volumes
    • Mocked mode: clusters reach Succeeded at once with a synthetic kubeconfig; no Docker required

    Quickstart

    1: Create a cluster

    curl -s -i -X PUT \
  "http://localhost:4577/subscriptions/my-sub/resourceGroups/my-rg/providers/Microsoft.ContainerService/managedClusters/my-cluster?api-version=2025-10-01" \
  -H "Content-Type: application/json" \
  -d '{
    "location": "eastus",
    "properties": {
      "kubernetesVersion": "1.36",
      "dnsPrefix": "my-cluster-dns",
      "agentPoolProfiles": [
        {"name": "nodepool1", "count": 1, "vmSize": "Standard_DS2_v2", "mode": "System"},
        {"name": "userpool", "count": 2, "vmSize": "Standard_D4s_v5", "mode": "User",
         "nodeLabels": {"team": "payments"}, "nodeTaints": ["dedicated=batch:NoSchedule"],
         "availabilityZones": ["1", "2"]}
      ]
    }
  }'

    The response is 201 with provisioningState: Creating and an Azure-AsyncOperation header. In real mode the cluster reaches Succeeded once the API server answers /readyz and every node is Ready (about 30 to 90 s, longer when images are pulled). In mocked mode it is Succeeded at once.

    2: Wait for the operation

    OP=$(curl -s -D - -o /dev/null -X PUT ... | awk -F': ' 'tolower($1)=="azure-asyncoperation" {print $2}' | tr -d '\r')
until [ "$(curl -s "$OP" | python3 -c "import sys,json; print(json.load(sys.stdin)['status'])")" != "InProgress" ]; do
  sleep 5
done

    Clients that poll long-running operations (the SDKs, az, Terraform) do this for you.

    3: Get the kubeconfig

    curl -s -X POST \
  "http://localhost:4577/subscriptions/my-sub/resourceGroups/my-rg/providers/Microsoft.ContainerService/managedClusters/my-cluster/listClusterUserCredential?api-version=2025-10-01" \
  | python3 -c "import sys,json,base64; print(base64.b64decode(json.load(sys.stdin)['kubeconfigs'][0]['value']).decode())" \
  > ~/.kube/my-cluster.yaml
kubectl --kubeconfig ~/.kube/my-cluster.yaml get nodes -L agentpool,topology.kubernetes.io/zone

    NAME                                STATUS   ROLES    AGE   VERSION        AGENTPOOL   ZONE
aks-nodepool1-12345678-vmss000000   Ready    <none>   40s   v1.36.6+k3s1   nodepool1   0
aks-userpool-12345678-vmss000000    Ready    <none>   40s   v1.36.6+k3s1   userpool    eastus-1
aks-userpool-12345678-vmss000001    Ready    <none>   40s   v1.36.6+k3s1   userpool    eastus-2

    In real mode the credential operations answer 409 OperationNotAllowed until the cluster has a kubeconfig (while it is first Creating, or after it Failed), rather than a kubeconfig that cannot reach a server.

    4: Delete the cluster

    curl -s -i -X DELETE \
  "http://localhost:4577/subscriptions/my-sub/resourceGroups/my-rg/providers/Microsoft.ContainerService/managedClusters/my-cluster?api-version=2025-10-01"
# 202 with Azure-AsyncOperation and Location; the cluster shows Deleting until its containers,
# volumes and network are gone, then GET answers 404

    Lifecycle and long-running operations

    Request Answer Operation
    PUT cluster (new) 201, Creating, Azure-AsyncOperation, Retry-After InProgress until the API server and the nodes are ready
    PUT cluster (existing) 200, Updating (or Upgrading for a version change) the change is applied: pool counts, labels, taints, zones, versions
    PUT agent pool 201/200, Creating, Updating, Scaling or Upgrading, Azure-AsyncOperation the pool's nodes are created, removed or recreated
    DELETE cluster or agent pool 202, Azure-AsyncOperation, Location; 204 when absent containers removed, then the resource
    POST stop / start 202, Location containers stopped or started; powerState.code is Stopped or Running

    The operation status (GET .../operations/{id}) follows the provisioning state of the cluster: InProgress while it is transient, Succeeded when it settles, Failed with the error message otherwise (for example when the kubeconfig cannot be read from k3s, or the nodes do not become Ready within ready-timeout-seconds). The Location monitor (.../operationresults/{id}) answers 202 while running and 204 once done, as the ManagedClusters_Start example shows. A PUT that arrives while another is applied is applied after it, and a PUT on a cluster that is Deleting fails with 409 OperationNotAllowed.

    Restore. With a persistent storage mode (persistent, hybrid, wal), every recorded cluster is reconciled at startup: surviving server and agent containers are adopted; a lost server is recreated on its data volume (same CA, same kubeconfigs); a lost volume gives a fresh cluster and a warning that its CA changed. In memory mode nothing is restored. Shutdown still removes the containers unless keep-running-on-shutdown is set.

    Kubernetes versions

    AKS supports the four newest minors; on 2026-11-10 they are 1.34 (end of life November 2026), 1.35, 1.36 and 1.37, and the portal, CLI and PowerShell create clusters on N-1 (AKS release calendar). The emulator runs one pinned k3s image per minor:

    kubernetesVersion Runs k3s image
    1.34 or 1.34.13 1.34.13 rancher/k3s:v1.34.13-k3s1
    1.35 or 1.35.10 1.35.10 rancher/k3s:v1.35.10-k3s1
    1.36 or 1.36.6 (default) 1.36.6 rancher/k3s:v1.36.6-k3s1
    1.37 or 1.37.2 1.37.2 rancher/k3s:v1.37.2-k3s1

    Patch numbers follow k3s, not AKS's own patch releases. kubernetesVersion echoes what was asked (major.minor or the exact patch) and currentKubernetesVersion the patch that runs, as the REST spec describes ("When <major.minor> is specified, the latest supported GA patch version is chosen automatically"). The rules AKS applies:

    • Upgrades go one minor at a time and never down; asking for the same minor again is no upgrade.
    • An upgrade (a new kubernetesVersion on PUT) recreates the k3s server on the new image with the same data volume and host port, so existing kubeconfigs keep working, then recreates the nodes of every pool under their own names.
    • An agent pool orchestratorVersion change (agent pool PUT) recreates that pool's nodes only. A pool may lag the control plane by up to three minors and never lead it (version skew).
    • Through the managed cluster API, pools name no orchestratorVersion or each name one that is unchanged or equal to the control plane's; per-pool changes go through the agent pool API.
    Case HTTP Code Message (as AKS words it)
    Unsupported cluster version 400 K8sVersionNotSupported Managed cluster <name> is on version <v> which is not supported in this region. Please use [az aks get-versions] command to get the supported version list in this region. For more information, please check https://aka.ms/supported-version-list (example)
    Unsupported pool version 400 AgentPoolK8sVersionNotSupported Version <v> is not supported in this region. Please use [az aks get-versions] ... (example)
    Skipped or lower minor 400 OperationNotAllowed Upgrading Kubernetes version <from> to <to> is not allowed. Available upgrades: [<versions>]. Please see https://aka.ms/aks-supported-k8s-ver for version details. (example)
    Pool ahead of, or more than three minors behind, the control plane 400 NodePoolMcVersionIncompatible Node pool version <p> and control plane version <c> are incompatible. Minor version of node pool version <n> is bigger than control plane version <m>. ... (error codes, example)
    Mixed or changed pool versions through the managed cluster API 400 NotAllAgentPoolOrchestratorVersionSpecifiedAndUnchanged Using managed cluster api, all Agent pools' OrchestratorVersion must be all specified or all unspecified. ... (example)

    The wording of the "more than three minors behind" message is not verified.

    kubernetesVersions, upgradeProfiles/default and availableAgentPoolVersions have the shapes of the KubernetesVersions_List, ManagedClustersGetUpgradeProfile and AgentPoolsGetAgentPoolAvailableVersions examples and list only the versions above.

    Agent pools as nodes

    The k3s server runs with --disable-agent --egress-selector-mode=cluster: it has no kubelet, so kubectl get nodes lists only agent pool nodes, as on AKS, and the API server reaches kubelets, pods and services through the agents' tunnels (pod logs and the metrics API work through them). Each node is a k3s agent container on the cluster's Docker network floci-aks-<instanceId>; the server also joins the emulator's own network when one is configured.

    Node field Value
    Name aks-<pool>-<8 digits>-vmss<instance>: the scale set's computer name prefix followed by the instance ID in base 36 over six characters (labels, VMSS instance names)
    spec.providerID azure:///subscriptions/<sub>/resourceGroups/<node resource group, lowercased>/providers/Microsoft.Compute/virtualMachineScaleSets/aks-<pool>-<digits>-vmss/virtualMachines/<index> (the Azure cloud provider lowercases the resource group, cloud-provider-azure)
    Taints the pool's nodeTaints (key=value:Effect, validated)
    CPU and memory the container's limits come from the VM size (for example Standard_D4s_v5: 4 vCPU, 16 GiB), capped at the Docker host's CPUs
    max-pods the pool's maxPods, defaulting from the network plugin (see Networking)

    Labels, from AKS's reserved system labels:

    Label Value
    kubernetes.azure.com/agentpool, agentpool (deprecated, still set) pool name
    kubernetes.azure.com/mode system or user
    kubernetes.azure.com/role agent
    kubernetes.azure.com/cluster node resource group (MC_<rg>_<cluster>_<region> by default)
    kubernetes.azure.com/managedby aks
    kubernetes.azure.com/os-sku the pool's osSKU (Ubuntu by default)
    kubernetes.azure.com/nodepool-type VirtualMachineScaleSets
    kubernetes.azure.com/sku-cpu, kubernetes.azure.com/sku-memory vCPUs and GiB of the VM size
    node.kubernetes.io/instance-type, beta.kubernetes.io/instance-type VM size
    topology.kubernetes.io/region cluster location
    topology.kubernetes.io/zone <region>-<zone> for a zonal pool (nodes spread round-robin over availabilityZones), 0 otherwise
    kubernetes.azure.com/accelerator, accelerator (deprecated, still set) nvidia on GPU sizes
    pool nodeLabels as given; keys under kubernetes.azure.com/ and kubernetes.io/ are refused with 400 InvalidParameter, since AKS reserves those prefixes

    Count changes (managed cluster or agent pool PUT) add nodes at the next indexes or remove the highest ones; an agent pool DELETE removes its nodes; a pool with count: 0 has no node. Label and taint changes are applied to the running nodes, and labels or taints a previous request set and this one drops are removed.

    VM sizes the emulator knows by heart: DSv2 (DS1 to DS5), Dsv5 (D2s to D32s), NCasT4_v3, NC A100 v4, ND H100 v5 and NVadsA10 v5 (Azure VM sizes). Any other size takes its vCPU count from its name (the number after the family letters) and 8 GiB per vCPU for the E family, 2 GiB for F, 4 GiB otherwise.

    Node cap. max-nodes-per-cluster (default 5) bounds the node containers of a cluster. System pools are served first, then the others in creation order; pools past the cap get fewer nodes, the API still reports their requested count, and a WARN names the cap and the pools short of nodes.

    GPU sizes

    Nodes of NC, ND and NV sizes (except the AMD NVv4 and MI300X sizes) carry kubernetes.azure.com/accelerator=nvidia (labels) and advertise the size's GPU count as nvidia.com/gpu capacity and allocatable, so pods with resources.limits: {nvidia.com/gpu: 1} schedule on them (the container still has no GPU). On AKS that capacity appears once the NVIDIA device plugin runs, which AKS installs on AKS-managed GPU node pools and which you install yourself otherwise (Use GPUs on AKS); the emulator advertises it directly. AKS adds no taint to GPU nodes; its examples add sku=gpu:NoSchedule through nodeTaints, which the emulator applies like any other taint.

    Storage classes

    k3s's own local-path class is disabled. A k3s auto-deploy manifest creates the classes AKS precreates, and a local-path-provisioner instance registered under each Azure CSI driver name (disk.csi.azure.com, file.csi.azure.com) serves them from a Docker volume every node mounts, so claims bind, data survives a node being recreated, and file shares are ReadWriteMany across nodes.

    Class Provisioner Parameters Binding mode
    default (default class) disk.csi.azure.com skuname: StandardSSD_LRS WaitForFirstConsumer
    managed-csi disk.csi.azure.com skuname: StandardSSD_LRS WaitForFirstConsumer
    managed-csi-premium disk.csi.azure.com skuname: Premium_LRS WaitForFirstConsumer
    managed-csi-premium-v2 (Kubernetes 1.35 and later) disk.csi.azure.com skuname: PremiumV2_LRS, cachingMode: None WaitForFirstConsumer
    managed disk.csi.azure.com cachingmode: ReadOnly, kind: Managed, storageaccounttype: StandardSSD_LRS WaitForFirstConsumer
    managed-premium disk.csi.azure.com cachingmode: ReadOnly, kind: Managed, storageaccounttype: Premium_LRS WaitForFirstConsumer
    azurefile-csi file.csi.azure.com skuName: Standard_LRS Immediate
    azurefile-csi-premium file.csi.azure.com skuName: Premium_LRS Immediate
    azurefile file.csi.azure.com skuName: Standard_LRS Immediate
    azurefile-premium file.csi.azure.com skuName: Premium_LRS Immediate

    All have reclaimPolicy: Delete, allowVolumeExpansion: true and the labels addonmanager.kubernetes.io/mode: EnsureExists and kubernetes.io/cluster-service: "true". Sources: storage concepts (default is managed-csi, premium v2 from 1.35, Delete and expandable), Azure Disks (WaitForFirstConsumer, skuName values, PremiumV2_LRS only with caching None), Azure Files (Immediate), and a kubectl get sc listing from an AKS cluster for the legacy names managed, managed-premium, azurefile, azurefile-premium, the managed-premium parameters and the labels. Not verified: the parameters of managed, azurefile and azurefile-premium. Not emulated: from Kubernetes 1.29, AKS uses ZRS SKUs in the built-in disk classes of zonal clusters; the emulator keeps LRS. The Blob CSI classes (azureblob-*) exist on AKS only when the Blob driver is enabled and are not created.

    Networking

    A new cluster's networkProfile is completed with AKS's defaults and applied to the k3s server:

    Field Default Applied as
    networkPlugin / networkPluginMode azure / overlay (Azure CNI Overlay) reported; pods still use k3s's flannel
    podCidr (or podCidrs[0]) 10.244.0.0/16 for overlay, kubenet and none; none reported for Azure CNI on the node subnet --cluster-cidr (10.244.0.0/16 when none is reported)
    serviceCidr (or serviceCidrs[0]) 10.0.0.0/16 --service-cidr; the kubernetes service is 10.0.0.1
    dnsServiceIP 10.0.0.10 --cluster-dns; the kube-dns service address
    networkPolicy / networkDataplane none k3s's network policy controller runs only with a policy engine (azure, calico, cilium) or the Cilium dataplane, since AKS enforces NetworkPolicies only then
    outboundType loadBalancer reported
    loadBalancerSku standard reported

    GET also reports podCidrs, serviceCidrs and ipFamilies: ["IPv4"], as the ManagedClustersGet example does. A dnsServiceIP outside serviceCidr fails with 400 DnsServiceIpOutOfServiceCidr "The DNS service IP 10.0.0.10 is out of the range defined by service CIDR 10.200.0.0/16." (troubleshooting); a malformed range fails with 400 InvalidParameter. Pools default maxPods from the plugin: 250 for Azure CNI Overlay and none, 30 for Azure CNI on the node subnet, 110 for kubenet (az aks create, overlay).

    Sources: REST spec (defaults 10.244.0.0/16, 10.0.0.0/16, 10.0.0.10, loadBalancer), Azure CNI Overlay ("If you don't specify --network-plugin, AKS defaults to Azure CNI Overlay", default pod CIDR), az aks create.

    Not verified, so kept simple: AKS does not document what a later PUT that changes the ranges answers; the emulator keeps the ranges the cluster was created with. Dual-stack (IPv6) ranges are not emulated: the first IPv4 range is used. Clusters recorded before this change keep k3s's own ranges (10.42.0.0/16, 10.43.0.0/16), since their data store was initialized with them. metrics-server runs, as AKS ships it; traefik does not.

    A pod reaches a Service whose endpoint is on its own node, cluster DNS included, only when the Docker host's kernel has br_netfilter loaded: without it, the reply between two pods of a node is bridged past conntrack, so the Service's address translation is never reversed and the connection times out. Docker loads the module only for features that need it, k3s cannot load it from its container, and k3s's network policy controller, which loads it as a side effect, is off unless the cluster names a policy engine. Every k3s container therefore makes the host kernel load it (a throwaway iptables physdev rule) before k3s starts. When that fails, the container's log says floci-az: br_netfilter is not loaded on the Docker host, and sudo modprobe br_netfilter on the host fixes it.

    Credentials

    Both credential operations return one kubeconfig, base64-encoded, laid out as AKS writes it (an az aks get-credentials recording and the az CLI merge test):

    Operation kubeconfigs[0].name Cluster and context User
    listClusterUserCredential clusterUser <cluster> clusterUser_<resourceGroup>_<cluster>
    listClusterAdminCredential clusterAdmin <cluster> clusterAdmin_<resourceGroup>_<cluster>

    az aks get-credentials --admin renames the admin context to <cluster>-admin itself when it merges the file, as on AKS. Both users carry the cluster's k3s client certificate (cluster admin): on AKS without Microsoft Entra integration the user credential is a certificate with the same rights. The server is the endpoint clients reach the API server on, not <dnsPrefix>.hcp.<region>.azmk8s.io:443.

    With disableLocalAccounts: true, listClusterAdminCredential fails with 400 BadRequest "Getting static credential is not allowed because this cluster is set to disable local accounts." (local accounts, raw error); setting it back to false gives the admin credential back. On a cluster without Microsoft Entra integration the user credential fails the same way, since the docs say "any attempt to authenticate with user or admin credentials will fail" (the exact body of that case is not verified). On an Entra cluster the user credential is the kubelogin kubeconfig described below.

    Microsoft Entra ID and Azure RBAC

    aadProfile

    Field Behavior
    managed Turns managed Entra integration on; once on it stays on, since AKS can't disable it (control plane authentication)
    enableAzureRBAC Authorizes Kubernetes requests against Azure role assignments (below)
    adminGroupObjectIDs Bound to cluster-admin; answered null when none were sent, as the spec example ManagedClustersCreate_UpdateWithEnableAzureRBAC.json shows
    tenantID Defaults to the subscription's tenant
    clientAppID, serverAppID Legacy fields, stored and returned
    serverAppSecret Stored, never returned (x-ms-secret)

    A PUT that omits aadProfile keeps it. Not verified: the RP's errors for enableAzureRBAC without managed, a tenantID other than the subscription's, or a request that turns integration off (the emulator keeps it on).

    User kubeconfig

    On an Entra cluster listClusterUserCredential returns an exec user, as AKS writes it from Kubernetes 1.24 (kubelogin authentication):

    users:
- name: clusterUser_<resourceGroup>_<cluster>
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1beta1
      args: [get-token, --environment, AzurePublicCloud, --server-id, 6dae42f8-4368-4678-94ff-3960e28e3630,
             --client-id, 80faf920-1908-4b52-b5ef-a8e7bedfc67a, --tenant-id, <tenantID>, --login, devicecode]
      command: kubelogin

    6dae42f8-... is the AKS server application, the audience of every kubelogin mode, and 80faf920-... the public client. The az CLI looks for --login devicecode and converts the file to -l azurecli when kubelogin is installed. format=azure returns the legacy azure auth-provider user (apiserver-id, client-id, tenant-id, environment, config-mode: '1'), the keys kubelogin's convert-kubeconfig reads. The admin credential stays the certificate kubeconfig. The installHint, env and provideClusterInfo fields are written as commonly observed in AKS kubeconfigs; not verified against a Tier 1 source.

    kubelogin reaches floci-az only over HTTPS (azidentity refuses a plain HTTP authority) and with --disable-instance-discovery (MSAL otherwise asks login.microsoftonline.com about the host and gets AADSTS50049). Either:

    • convert to the az CLI mode once the az CLI is signed in to floci-az: kubelogin convert-kubeconfig -l azurecli;
    • or set floci-az.services.aks.entra.kubeconfig-floci-authority=true (with floci-az TLS on), which appends --authority-host https://<floci-az>/ --disable-instance-discovery to the kubeconfig. convert-kubeconfig drops those two flags for every mode except workloadidentity, so add them again after a conversion.

    Tested modes: spn, ropc and azurecli (compat suite compat-azcli/test/kubelogin.bats). devicecode and interactive need endpoints floci-az does not serve (device code) or a browser.

    Authentication

    An Entra cluster's API server runs with authentication-token-webhook-config-file pointing at POST /_floci/aks/clusters/{instanceId}/token-review, the role AKS's managed webhook plays (identity concepts). It does what that webhook (kubeguard/guard, auth/providers/azure) does:

    • the token must be signed by floci-az's Entra, within its lifetime, issued in the cluster's tenant, for the AKS server application (Entra issues v1.0 tokens with upn and groups for it, see Entra);
    • username = upn, else oid (service principals and managed identities appear by object id);
    • groups = the groups claim (object ids), else the directory's direct memberships; extra.oid = the object id.

    A refused token gets 401 Unauthorized. Service account tokens and the admin certificate never reach the webhook.

    Admin groups

    adminGroupObjectIDs become the ClusterRoleBinding aks-cluster-admin-binding-aad to cluster-admin, written to the k3s auto-deploy directory and rewritten when the list changes ("AKS automatically generates a ClusterRoleBinding that binds all of the listed groups to the cluster-admin Kubernetes role", identity concepts). Its name on AKS is not documented. With Azure RBAC the admin groups are "irrelevant", so the binding names no subject.

    Azure RBAC

    With enableAzureRBAC: true the API server runs authorization-mode=Node,RBAC,Webhook with its authorization webhook at POST /_floci/aks/clusters/{instanceId}/subject-access-review. Kubernetes RBAC answers first, so a RoleBinding still grants what it grants and the webhook decides the rest, the union AKS describes (authorization concepts). As guard does (authz/providers/azure):

    Request Data action checked
    get, list, watch on {group}/{resource} Microsoft.ContainerService/managedClusters/{group}/{resource}/read (no group segment for the core group)
    create, update, patch .../write
    delete, deletecollection .../delete
    bind, escalate, use, impersonate .../{verb}/action
    pods/exec .../pods/exec/action; other subresources check their resource
    non-resource path Microsoft.ContainerService/managedClusters/{path}/{action}

    The scope is <clusterId>/namespaces/<namespace> for a namespaced request, else the cluster id, and assignments at the cluster, its resource group or its subscription apply below them. The principals are the user's oid and its groups that are object ids. Users whose name starts with system: and users without extra.oid (service accounts, certificate users, k3s components) get no opinion, so Kubernetes RBAC decides for them. A denial reads, as kubectl prints it on AKS (PIM example):

    Error from server (Forbidden): pods is forbidden: User "<upn>" cannot list resource "pods" in API group "" in the
namespace "ns2": User does not have access to the resource in Azure. Update role assignment to allow access.

    The API server caches webhook answers for aks.entra.webhook-cache-ttl-seconds (5 s); AKS documents up to five minutes for an assignment to take effect. Wildcard requests (* verbs, resources or groups) are checked with the * kept in the data action, so only a role whose data actions match it by wildcard grants them; guard expands them from Azure's operations list. ABAC conditions are not evaluated.

    When floci-az is down, Entra users get 401 and Azure RBAC requests are refused; the admin certificate and k3s components keep working, since the webhooks never see them or give no opinion.

    Workload Identity

    OIDC issuer

    oidcIssuerProfile.enabled is on for new clusters, as AKS does from Kubernetes 1.34, the oldest version the emulator runs (OIDC issuer); enabled: false at creation keeps it off, and once on it stays on. issuerURL is https://{location}.oic.prod-aks.azure.com/{tenantId}/{uuid}/, with a uuid generated once per cluster and kept (deploy Workload Identity). Clusters stored before round 2 have no issuer until a PUT enables it.

    The k3s server signs service account tokens under that URL (service-account-issuer-=, which k3s prepends so tokens issued before stay valid), publishes {issuerURL}openid/v1/jwks as its JWKS URL, and follows AKS's token rules: no extended expiration and at most 24 hours. Enabling the issuer on an existing cluster replaces its server on the same data volume, as AKS restarts its API server. floci-az reads the cluster's JWKS after every reconcile and serves the issuer's documents, with the AKS fields (response_types_supported: ["id_token"], subject_types_supported: ["public"], RS256):

    Where Path
    The AKS host, when DNS sends {location}.oic.prod-aks.azure.com to floci-az {issuerURL}.well-known/openid-configuration, {issuerURL}openid/v1/jwks
    floci-az's own path /_floci/aks/oidc/{location}/{tenantId}/{uuid}/.well-known/openid-configuration and .../openid/v1/jwks

    floci-az's Entra resolves the issuer in-process, so federated credentials verify offline. rotateServiceAccountSigningKeys is not emulated.

    Enabling it

    securityProfile.workloadIdentity.enabled: true needs the issuer; without it the PUT fails with 400 "Enabling workload identity requires enabling OIDC issuer." (the az CLI checks this client-side; the RP's own error is not verified). Then:

    1. The upstream azure-workload-identity webhook v1.6.3 runs in kube-system as azure-wi-webhook-controller-manager, configured by azure-wi-webhook-config (AZURE_TENANT_ID = the cluster's tenant), as AKS's add-on does (overview). Its image is aks.workload-identity.webhook-image. Its serving certificate is pre-seeded the way cert-controller generates the ones it keeps, so it is Ready seconds after the cluster (about two minutes otherwise). Pods labelled azure.workload.identity/use: "true" under a service account annotated azure.workload.identity/client-id get AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_AUTHORITY_HOST, AZURE_FEDERATED_TOKEN_FILE (/var/run/secrets/azure/wi/<hash>/token/azure-identity-token from v1.6.1) and the projected token for api://AzureADTokenExchange. Which webhook version AKS runs today is not verified.
    2. A selector-less Service floci-az in kube-system points at floci-az (ports 443 and 80 to floci-az's port, where its TLS proxy tells HTTPS from HTTP), and floci-az's CA is published as the ConfigMap floci-az-ca (key ca.crt) in kube-system.
    3. Pods reach floci-az's Entra over HTTPS, since the Azure SDKs refuse a plain HTTP authority. floci-az's TLS must be on (FLOCI_AZ_TLS_ENABLED=true). Two modes (aks.workload-identity.entra-mode):
    Mode AZURE_AUTHORITY_HOST in pods What floci-az adds What the workload does
    microsoft-hostnames (default) https://login.microsoftonline.com/, AKS's value a coredns-custom override (key floci-az.override) that answers login.microsoftonline.com and the issuer host with the floci-az Service; those names in floci-az's certificate; Entra's instance discovery (common/discovery/instance) trusts floci-az-ca
    authority https://floci-az.kube-system.svc.cluster.local/, through an AzureStackCloud environment file the webhook reads (AZURE_ENVIRONMENT_FILEPATH) the Service name in floci-az's certificate trusts floci-az-ca, and disables instance discovery in code (azidentity has no environment variable for it)

    Turning Workload Identity off removes the add-on.

    The exchange itself: the SDK posts the projected token as client_assertion with the identity's client id, and floci-az's Entra checks it against the identity's federated identity credentials and answers with an access token for the identity, or Entra's AADSTS codes (Entra, client assertions). For the AKS subject, the credential's subject is system:serviceaccount:<namespace>:<service account>.

    Trusting floci-az's CA

    A projected volume cannot read another namespace, so copy floci-az-ca into the workload's namespace and mount it, then point the runtime at it: SSL_CERT_FILE (Go, OpenSSL, curl), REQUESTS_CA_BUNDLE (Python requests), NODE_EXTRA_CA_CERTS (Node.js), or a Java truststore. floci-az injects nothing into pods itself.

    kubectl get configmap floci-az-ca -n kube-system -o json \
  | jq '.metadata = {name: "floci-az-ca"}' | kubectl apply -n my-app -f -

    Networking and limits

    • When floci-az runs in a container, the server and the agents join its Docker network, so pods reach it by its address there. When it runs on a Linux host, pods reach it at the gateway of the cluster's own Docker network, the host's address on that bridge; on Docker Desktop, at the address host.docker.internal resolves to.
    • A coredns-custom ConfigMap of your own replaces floci-az's override (AKS documents that ConfigMap for your own customizations); keep the floci-az.override key in it.
    • Python, .NET, Java and JavaScript SDK behavior against the "Microsoft hostnames" mode is not verified; MSAL Go and azidentity are, and the end-to-end test exchanges the token with curl as the SDKs do.

    LoadBalancer Services

    New clusters run k3s without its servicelb (load-balancer.mode=emulated, recorded on the cluster), and floci-az plays AKS's cloud controller for Services of type LoadBalancer that name no loadBalancerClass (kubernetes/cloud-provider wantsLoadBalancer). Every 3 seconds it adds the service.kubernetes.io/load-balancer-cleanup finalizer, gives the load balancer an address and an appliance container holding it, writes status.loadBalancer.ingress: [{ip}], and reports the service controller's events (EnsuringLoadBalancer, EnsuredLoadBalancer, SyncLoadBalancerFailed, UpdatedLoadBalancer, UnAvailableLoadBalancer, DeletingLoadBalancer, DeletedLoadBalancer).

    Service Address (public LB, internal LB)
    default a public address from load-balancer.public-cidr (198.51.100.0/24, RFC 5737 TEST-NET-2), unique across every cluster of the emulator
    service.beta.kubernetes.io/azure-load-balancer-internal: "true" the address the cluster's Docker network gives the appliance
    service.beta.kubernetes.io/azure-load-balancer-ipv4, else the deprecated spec.loadBalancerIP that public address when it is in the range and free; otherwise the Service stays <pending> with a SyncLoadBalancerFailed event

    The appliance is a container from the cluster's own k3s image that DNATs each Service port to the Ready agent nodes' NodePorts (only those with a ready endpoint under externalTrafficPolicy: Local, never nodes labelled node.kubernetes.io/exclude-from-external-load-balancers), honours loadBalancerSourceRanges, and publishes each TCP port on a free host port, listed in the Service annotation floci.io/load-balancer-host-ports (TCP/80=127.0.0.1:41234). Deleting the Service, or changing its type, removes the appliance and then the finalizer; deleting the cluster removes every appliance, and the public network goes with the last public load balancer.

    From Public address Internal address
    A pod of the cluster yes (kube-proxy answers the status address) yes
    A container on the cluster network through the appliance's cluster-network address yes
    A container on floci-az-aks-lb-public yes no
    The host 127.0.0.1:<host port> from the annotation; on Linux also the address itself same

    load-balancer.mode=servicelb keeps k3s's servicelb (node addresses in the status) and off leaves Services pending. Clusters created before this mode existed keep servicelb when they are restored.

    Not emulated: the public IP and load balancer frontend resources in the node resource group (azure-pip-name, azure-dns-label-name and the other cloud-provider-azure annotations are accepted and ignored), a fixed internal address (internal load balancers take the appliance's address, since the cluster network has no configured subnet), UDP ports on the host, health probes, client IP preservation through the appliance, allocateLoadBalancerNodePorts: false, IPv6. The appliance runs privileged, like the cluster's own containers. AKS's load balancer names (kubernetes, kubernetes-internal) are not verified at Tier 1.

    Fields stored and echoed

    securityProfile (except workloadIdentity), apiServerAccessProfile, addonProfiles, autoUpgradeProfile, autoScalerProfile, linuxProfile, windowsProfile, workloadAutoScalerProfile, storageProfile, ingressProfile, azureMonitorProfile, identityProfile, httpProxyConfig and the client ID of servicePrincipalProfile (never its secret) are stored and returned as sent, with no runtime effect. Pool enableAutoScaling, minCount and maxCount are echoed; nothing autoscales.

    Architecture

    ┌────────────────────────────────────────────────────────────────────────┐
│  Your App                                                              │
│                                                                        │
│  ARM REST calls ──────► floci-az :4577 ──► AksHandler ──► reconciler   │
│  (create, scale, upgrade,                (state, LRO)    (containers)  │
│   get credentials)                                                     │
│                                                                        │
│  kubectl / k8s client ─────────► k3s server :6443 (no kubelet)         │
│                                  floci-az-aks-{instanceId}             │
│                                      │  network floci-aks-{instanceId} │
│                                      ├── k3s agent aks-nodepool1-…-vmss000000
│                                      └── k3s agent aks-userpool-…-vmss000000
└────────────────────────────────────────────────────────────────────────┘

    The management plane (ARM API) goes through floci-az on port 4577. The data plane (kubectl, Kubernetes API) connects directly to the k3s server on its allocated port: floci-az is not in the data path.
